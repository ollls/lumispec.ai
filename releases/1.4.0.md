# LLM Workbench v1.4.0

## Overview

A web-access release. Since v1.3.0 the workbench has gained a second way to reach the web: **Browser
Search**, a small Chrome extension that loads search-result pages and articles in a hidden tab of
the user's own browser and hands the rendered HTML back to the server. Because the request comes
from a real, logged-in Chrome with its real TLS fingerprint and cookies, Google, Bing, Brave,
DuckDuckGo and sites such as Reuters answer the way they answer a person — no faked headers, no
headless Puppeteer, no attestation-header guesswork (see `docs/google.md` for why that fight was
lost).

Browser Search is optional and off by default. The existing HTTP path (Tavily, Keiro, DuckDuckGo,
got-scraping, Puppeteer) is untouched and remains the fallback whenever the browser path cannot
answer. Around the feature, the plugin system learned two generic things it needed: one plugin can
**supersede** another, and a plugin can show a **live status line** and raise a **warning on
enable**.

> ⚠️ **Browser Search requires a Chrome extension that you install yourself** (Chrome, Edge, Brave or
> any Chromium browser; loaded unpacked from the `extension/` folder, no store listing). The
> step-by-step install, verify, update and remove guide is
> [`extension/README.md`](../extension/README.md). Without the extension the plugin still works —
> every call falls back to the HTTP path and says so — but you get none of the benefit.

Twelve commits on `browser-search` (2026-10-24 → 2026-10-25), 17 files, +1,372 / −112.

## 🌐 Browser Search — the web through your own Chrome

**What it is.** A new plugin group, `browser` (`src/tools/plugin-browser.js`), that registers
`web_search` and `web_fetch` — the same two tool names the LLM already knows — and serves them
through the extension instead of HTTP:

- `web_search` opens the chosen engine's results page in an **inactive** tab, the extension returns
  the rendered HTML, and the server parses it into `[{title, url, description}]` with linkedom.
- `web_fetch` opens the page the same way and runs the HTML through the existing Readability +
  Turndown pipeline, so the markdown the LLM sees has the same shape as before.
- One hidden tab at a time; the tab is closed as soon as it has been read.

**Engines.** DuckDuckGo, Brave, Bing and Google, chosen on the Browser Search card as a radio —
exactly one is active. Results are never merged, and the HTTP fallback already backs up a failing
engine, so a multi-select would only have implied a chain that added little.

**All engine knowledge lives server-side.** The extension knows nothing about search engines: its
only request is "load this URL, wait for it to render, give me the HTML". Per engine the server
holds the URL builder, the render waits (Brave is client-rendered and gets more), a `block()` check
for that engine's CAPTCHA / consent pages, and the parser. Adding or fixing an engine is a server
edit picked up by the watch restart — the extension needs reloading only when `extension/` itself
changes, and the card flags a connected extension whose version differs from the checkout.

**Pages that never finish loading.** The extension no longer waits for Chrome's load event alone.
After 4 s it probes the document every 1.5 s and reads it as soon as it is past `loading` with real
text; at the 20 s cap it takes a usable DOM rather than failing. newsroom.amd.com sat for 20 s fully
rendered while trackers kept the tab in `loading`.

**No immediate re-fetch.** A URL whose browser *and* HTTP attempts both failed is remembered for
90 s; the LLM's habitual immediate retry gets the cached reason at once instead of another 20 s +
15 s wait.

**Parser repair loop.** When an engine's parser finds nothing on a page the extension returned, the
page is saved to `logs/browser-debug/<engine>-<timestamp>.html` and the fallback reason names the
file. The server cannot load these engines itself (Brave answers it with HTTP 429), so this dump is
the only reliable view of what the browser saw. Brave's parser was repaired this way within minutes
of its first live failure — see **Maintenance** below.

**Bot walls.** A page that comes back as a challenge shell ("Please enable JS", "Just a moment",
"verify you are human") or with under 200 chars of text is re-read in the same tab after 0.8 s, +3 s,
+4 s before giving up. Measured on Reuters: the first fetch took 8.5 s and came back with the real
front page once the challenge cleared; the next fetches took 1.1–1.7 s because the challenge cookie
now lives in the profile.

**Fallback with disclosure.** If no extension is connected, the request times out
(`BROWSER_SEARCH_TIMEOUT_MS`, default 25 s), the engine fails or returns nothing, or a fetched page is
still a wall, the call runs the regular HTTP `runWebSearch()` / `runWebFetch()` (exported from
`plugin-web.js`) using the saved Web Search & Fetch settings. Every fallback is disclosed in the tool
result — a `fallback` field with the reason and a suffix on `sources` / `_tier` — so the Think stream
shows exactly what happened. Nothing falls back silently.

**Bridge.** `src/services/browserBridge.js` attaches a `ws` WebSocketServer to the main Express
server at `/ws/browser` (same port as the UI, live whenever the server runs, loopback only, optional
shared secret `BROWSER_SEARCH_TOKEN`). One extension connection at a time, newest replaces oldest,
protocol-level ping/pong every 30 s, id-correlated requests with per-request timeouts.

**Status.** A "Browser" dot in the top bar is green while the extension is connected. The Browser
Search card shows a live line — connected + version, disconnected + last seen, or "No browser
extension connected … install it from extension/README.md" — and enabling the plugin with nothing
connected raises a warning toast with the same pointer. The viewer's own browser is never checked:
the UI may run in Firefox while the extension runs in Chrome on the same machine.

**Privacy note.** Pages open in the user's logged-in profile, so a site the user is signed into will
show the assistant its signed-in content. Disable Browser Search for conversations where that is
not wanted. The extension only reads pages it opened itself and never touches other tabs.

## 🧩 Plugin system — supersession, card status, enable warnings

Three generic additions, all documented in `CLAUDE.md` under the plugin interface:

- **`supersedes: ['web']`** — while the declaring plugin is enabled, the listed groups are
  hot-unloaded (so it can re-register their tool names) and their slider is grayed out at its
  *saved* position with a "Replaced by …" note. Their `plugins.json` entries are never modified, so
  disabling the superseder restores them exactly as they were. Toggling a superseded group via the
  API returns an error; a config-only update (mode/engines) still saves. A superseding plugin is
  listed directly after the group it replaces.
- **`defaults.enabled`** is honored for plugins with no `plugins.json` entry, so a plugin that
  requires setup can ship off by default.
- **`cardStatus()`** → `{ ok, text }` renders a live line on the Plugins card; **`enableWarning()`**
  → string is returned as `warning` by the toggle route and shown as an error-styled toast.
- Plugins now declare their panel controls via **`configUi()`** → `{ modes?, availableEngines?,
  engineMode? }` instead of a web-only hardcode in the registry; `engineMode: 'single'` renders
  radios. The toggle route validates engine ids by shape only — each plugin filters its own.

`unregisterPlugin()` only drops tool entries the group owns, since a superseder reuses the same
names.

## 🧩 Chrome extension — `extension/`

Manifest V3, loaded unpacked, version 0.4.0. Files: `manifest.json`, `background.js` (service
worker), `popup.html` / `popup.js`, `README.md`.

- Permissions: `tabs`, `scripting`, `storage`, `alarms`; host access `<all_urls>` so `web_fetch` can
  read any page the assistant asks for.
- Keeps the WebSocket open with reconnect/backoff; a `connecting` guard and per-socket ownership
  checks prevent the connection churn that an early build showed when the worker started from
  several triggers at once.
- Popup: connection state and version, server URL and token, enable toggle, and a **Test** box that
  loads any URL in a hidden tab and reports title, load time, text/HTML size and wall status —
  proves the install without the server.
- The README covers install (`chrome://extensions` → Developer mode → Load unpacked → the
  `extension` folder), verify, update (Reload button), disable, remove, troubleshooting and
  security notes.

## 🔧 Maintenance — search-engine parsers need periodic validation

Browser Search reads real result pages, so each engine's parser depends on that engine's HTML.
When an engine redesigns, its parser stops finding results. This is expected upkeep, and the
release is built to make it cheap and harmless:

- A failing parser never takes search down: the call falls back to HTTP and the result says
  `fallback: "<engine>: no results (page saved to logs/browser-debug/…)"`.
- The saved page gives the real markup; the fix is one entry in the `ENGINES` table of
  `src/tools/plugin-browser.js`, picked up by the watch restart — no extension change, no reload.
- Stability so far: DuckDuckGo's HTML endpoint, Google's organic `a h3` results and Bing's
  `li.b_algo` list have held for years; Brave (a Svelte app with hashed class names) is the one to
  expect to move. The Brave parser in this release was matched against a page saved on
  2026-10-25.

**Checklist for maintainers after each pull:** run one search per engine in use and confirm
`sources` reads `Browser (<engine>, … ms)` with no `fallback` key. If one fails, open the dump named
in the reason and adjust that engine's selectors.

## ⚙️ Configuration

| Variable | Default | Meaning |
|---|---|---|
| `BROWSER_SEARCH_TOKEN` | unset | Optional shared secret the extension must send as `?token=` on `/ws/browser`. Set the same value in the extension popup. |
| `BROWSER_SEARCH_TIMEOUT_MS` | 25000 | How long `web_search` / `web_fetch` wait for the extension before falling back. Raise to ~40000 for very slow sites. |

**Dependency change:** new runtime dependency `ws` `^8.22.0`. Run `npm install` after upgrading.

**Upgrade path:** `git pull` → `npm install` → restart → load the extension from `extension/` per
[`extension/README.md`](../extension/README.md) → enable **Browser Search** in Plugins and pick an
engine. The Browser dot turns green within a few seconds of the extension connecting.

## ✅ Validation

- Supersession: six toggle scenarios scripted against the registry (enable/disable, saved-off group
  stays off, config-only update on a paused group, startup with the superseder saved on), plus a
  stub-tool execution and system-prompt section swap.
- Bridge + plugin, against a fake extension client: token rejection (401), offline fallback with
  reason, CAPTCHA → fallback, fetch → markdown, thin-page fallback, hung-extension timeout, reconnect
  status and "last seen" reason, outdated-extension card flag.
- Engine parsers, against synthetic result pages: all four return decoded URLs and snippets (DDG
  `uddg=`, Bing `/ck/a?u=a1<base64url>`, Google `/url?q=`), Brave gets its longer render waits,
  Bing's "WEB" snippet prefix is stripped.
- Live, in the author's Chrome: Google searches in 0.5–1.1 s; Bing searches in 0.6–3.8 s with
  decoded links; Brave parser verified against a saved live page (8/8 results with titles and
  snippets) after its first guessed version failed; Reuters front page fetched through an 8.5 s
  challenge wait, then 1.1–1.7 s on later fetches; Guardian and BBC articles fetched in 1.2–1.8 s.
  Bing's answer to a query starting with "top" was dictionary entries for the word "top" — verified
  to be Bing's own result, not a parser fault.
- Debug dump, no-retry cache and interactive-page read: scripted against a fake extension (empty
  parse saves a named file; a failed URL is not re-fetched within 90 s; a hung page falls back
  once, not twice).

**Known and unfixed:** test scripts that exercise the fallback path make real HTTP search calls.
Search-engine parsers will need periodic re-validation — see **Maintenance** above.
