# LLM Workbench v1.6.5

## Overview

One fix after v1.6.4: **Brave search works again** in Browser Search. Since 2026-11-22 Brave
hides the address of every result, and every Brave search fell back to HTTP search. The
extension now reads the addresses in the page. **The extension must be reloaded** (0.7.0 →
0.8.0).

Five commits on `dev` since v1.6.4 (2026-11-21), 13 files, +339 / −19.

## 🦁 Brave search works again

**What happened.** On 2026-11-22 Brave Search changed its results page. Titles and snippets
are still there, but each result links to `search.brave.com/go/v1#<encrypted token>` instead
of the site. The real address is nowhere in the page; a script on the `/go/v1` page decrypts
the token and then goes to the site. Our parser found 20 results with no usable link and
reported "no results", so every search was answered by the HTTP fallback after a wasted
hidden tab.

**The fix.** The browser already knows how to follow those links, so the extension lets it:

- For each result link, the extension loads the redirect in an off-screen frame of the
  results page, reads where the frame is about to go, and **cancels the navigation**.
- The address is written on the link, and the server's Brave parser reads it from there.
- **The result sites are never contacted** by a search, only Brave is.
- **No new extension permission.** The step runs inside the results page.
- Up to 12 links are resolved per search, for the 8 results a search returns.

**Clearer failures.** A Brave search that still finds nothing now says why:

- *"needs Browser Search extension 0.8.0 or later"*: the connected extension is older.
  Reload it.
- *"none of N result links could be resolved"*: Brave changed its redirect page again.
  Switch the engine on the Browser Search card for now.

Both still fall back to HTTP search, as before.

**For developers.** The extension stays engine-agnostic. `fetch` takes a new generic option,
`resolveLinks: { selector, limit }`, advertised as the `resolve` capability; an engine entry
in the `ENGINES` table of `src/tools/plugin-browser.js` opts in by naming its links. Brave is
the only one that does.

## 📝 Also

- `data/templates.json` gains a **Digital Watch 2** template: the page is as tall as the
  watch, not the frame it is shown in.
- The first **Digital Watch** template no longer stops between 12:00 and 12:59. A variable
  declared `const` was assigned in those hours, an error on every tick.

## ✅ Validation

`npm test`: 192/192, six more than v1.6.4: five for the Brave parser and the failure
reasons, one for the new option on the extension bridge.

Live, on 2026-11-23 with extension 0.8.0 and Brave selected: eleven searches through the app,
eleven answered by Brave, 8 results each, 2.7–3.1 s per search, no fallback. All 48
distinct addresses in the six scripted searches were real site addresses, none a redirect
link or a Brave page.

The resolving step alone was measured in a foreground tab before it was built into the
extension: 8 links in about 140 ms, 24 of 24 over three runs.

Not tested: how Brave's bot check reacts to many searches in a row. The eleven above ran
within about five minutes without one.

The system prompt is unchanged from v1.6.4. No `.env` change.
**Upgrade:** `git pull` → restart → **reload the extension** at `chrome://extensions`
(the Browser Search card shows a button for it) → hard-reload the page.
