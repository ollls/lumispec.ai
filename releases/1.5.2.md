# LLM Workbench v1.5.2

## Overview

A one-fix patch on v1.5.1: **a task-pipeline step whose incoming context was clipped used to be told
so only by a tail marker it ignored.** The clip now announces itself to you and to the model, naming
what was lost. The v1.5.0 notes still describe everything else; v1.5.1 fixed Bing.

Two commits on `dev` since v1.5.1 (2026-11-03 and 2026-11-04), 11 files, +272 / −21.

---

## 🐛 A clipped hand-off was silent

The pipeline hands each step the previous step's output, capped at `MAX_PREV_RESULT_CHARS`
(32,000 by default). For a subtask group the siblings' outputs are joined under `## <subtask>`
headers **before** the cap applies and the cut is a head cut, not a window — so a wide fan-out
loses its last siblings whole.

On 2026-11-03 a pipeline fetched 13 news fronts as 13 isolated subtasks (3–5.6K chars each),
merged them to 60,357 chars, and the dashboard step received the first 32,000: seven outlets and
half of an eighth. It built a "World News" dashboard from those eight and presented them as the
whole set. The only trace was a `[...truncated from 60357 chars]` line at the very bottom of its
user message, below 32K chars of headlines. The model never mentioned it.

Every link in the chain now carries the fact:

| Where | What you see |
|---|---|
| Server log | `[task-processor] Task 3: Previous output truncated: showing the first 32,000 of 60,357 chars — cut mid-section: "Fetch NBC" — dropped entirely (5): "Fetch Bloomberg", …` |
| SSE stream | a new `{context_truncated: { from, cap, cut, dropped, notice }}` event before the step's first token |
| Chat UI | a persistent amber line under the step, live and again on re-render (stored on the step's `taskRun` entry as `contextTruncated`) |
| The model | its previous-output block now **opens** with `> ⚠ Previous output truncated … Work with what is here. State in your output which sections were missing or incomplete — do not present a partial set as the whole.` |

The clip itself is `truncatePrevResult()` in the new `src/services/pipelineContext.js`: pure, takes
the merged text and the cap, returns the text to hand the model plus the section the cut landed
inside and every section that starts at or after the cap. A flat step's prose has no sections, so
the notice then names only the counts.

Nothing about the cap changed. `MAX_PREV_RESULT_CHARS` is now documented in `.env.example` with the
accumulation rule: size it for siblings × per-subtask output, or keep the subtasks terse ("at most
6 headlines, one line each"). Raising `--ctx-size` does not raise it.

`docs/TASKMASTER.md` described the old tail marker and a stale line number; it now describes the
head cut and the signals. `CLAUDE.md` has a **Hand-off truncation** paragraph under Task Pipeline.

## 📄 World NEWS template

`data/templates.json` gains the **World NEWS** HTML template — the eight-outlet dashboard from the
2026-10-31 run (source badges, type tags, filter chips, search), the one on the README screenshot.
Insert it with `[template: World NEWS]` and the model fetches fresh fronts and refills it.

## ✅ Validation

`test/pipelineContext.test.js`: group cut inside a sibling with later siblings dropped, cut exactly
on a section boundary, flat prose with no sections, nested `###` headers not mistaken for sections,
and the no-clip pass-through. `npm test`: 55/55 (50 at v1.5.1 + 5).

No `.env` change required, no extension change, no reload. **Upgrade:** `git pull` → restart;
hard-refresh the chat UI once so `app.js` picks up the amber line.
