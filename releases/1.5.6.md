# LLM Workbench v1.5.6

## Overview

One tool result can no longer sink a turn. A `tree` of a 7,000-file repository used to land in the
prompt whole (428K chars, ~110K tokens); the next request was 131K tokens against a 64K slot and
llama-server answered 400. Three guards now sit between a tool and the prompt.

Two commits on `dev` since v1.5.5 (2026-11-08), 10 files, +259 / −14.

---

## 🧱 Tool result limits

- **`tree` is summarized over 300 files**: the top-level layout with counts, the first 300 paths,
  and how to see more. `source_read` gains an optional `path` for `tree` to list one subdirectory
  (escape-guarded). The llama.cpp tree that was 428K chars is 14.5K.
- **A ceiling in the executor.** Every serialized tool result is capped at 50,000 chars (~12K
  tokens). Over that, the model gets a small envelope with the original size and the head of the
  result, sized so JSON escaping cannot push it back over the ceiling.
- **The wind-down fits the prompt.** After trimming old results, if the prompt is still over 90% of
  the slot — the newest results are what blew the budget — every tool result is cut to 4,000, then
  1,500, then 400 chars, re-measured with llama's tokenizer after each pass, until it fits. Both the
  chat loop and the task pipeline. The "answer with what you have" request can never itself exceed
  the slot.

Pure helpers in `services/toolResultLimits.js`, covered by `test/toolResultLimits.test.js`.
