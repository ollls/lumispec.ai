# LLM Workbench v1.5.0

## Overview

Two features on top of v1.4.2, both about the browser the user already has open. (A v1.4.3 with
the first of them was prepared and folded in here; it was never tagged.)

**`web_fetch` can return a page as it reads on screen.** The v1.4.2 extractor fixes made news
fronts readable; the next real request — "list my top 70 Gmail subjects" — showed the other half
of the problem. Gmail loaded fine, signed in, through the extension, and still cost 19 fetches and
16 rounds, because the article extractor keeps every text node in the DOM and a Gmail inbox row is
~500 characters of hidden tooltips, accessibility labels and image links around a sender and a
subject the user sees as one line. `web_fetch` takes an optional `view`: `article` (the default,
unchanged) or `text`, one trimmed line per visual row. The same request now costs about three
fetches.

**The model can read a tab you have open — Tab Fetch.** The hidden-tab fetch stays the default
and the only path that runs on its own. Some pages it cannot reach by address: your bank after
login and two-factor, Gmail search results, a board you filtered by hand, a feed you scrolled.
You open and prepare the page; the model reads *that tab*, in place. It never navigates, clicks,
types, scrolls or closes anything in your tabs; it lists them only while you allow it; it asks
before each read unless you turn that off; and when several tabs could be the one you meant, it
asks instead of guessing. Design and plan in [`docs/TAB_FETCH.md`](../docs/TAB_FETCH.md).

Nothing in both is site-specific: the text view reads Google News five times denser too, and the
tab rules were validated with six tabs open including two banks. The extension changed (0.7.0), so
**Browser Search needs one reload** on `chrome://extensions` after pulling; the Plugins card says
so until you do. No new dependencies, no `.env` change. The README screenshot was replaced with
the full app around a news dashboard.

Ten commits on `dev` since v1.4.2 (2026-10-31), 24 files, +1,537 / −128.

## 👁️ `web_fetch` view: "text"

**Two views, one tool.** `view: "article"` is what every fetch did before: Readability for an
article, the headline-link list for a front page. `view: "text"` returns the page as it is laid
out on screen — hidden elements excluded, one line per visual row, table and grid cells joined
with ` · `. The tool descriptions and a routing line say when to use which: `text` for web
applications (mail, calendars, dashboards, boards) and whenever an `article` result comes back as
repeated fragments and image links; page through an application with its own date or filter URLs,
since invented pagination parameters are ignored. The result carries `view`. A parameter rather
than a second tool because the model already reaches for one: during the news run it invented
`extractMode: "markdown"` on its own.

**Where the text comes from.** The extension sends `document.body.innerText` alongside the HTML.
`innerText` is computed by Chrome's layout engine, so CSS-hidden tooltips and labels are already
gone and each visual row ends in a line break. The HTTP tier (Web Search & Fetch on its own, or the
fallback) approximates it from the markup and says so in `note`.

**When Chrome has not laid the page out.** In an inactive tab Chrome skips layout for virtualized
lists, and `innerText` only returns text that has layout: Gmail's loaded inbox reported 593 chars
of `innerText` against 24K chars of readable DOM text (body minus script/style/noscript/template,
reported as `domChars`). When `innerText` covers under 10% of the readable text, the extension
walks the DOM itself: subtrees whose computed style is `display: none` or `visibility: hidden`, or
that are `aria-hidden`, are dropped; blocks become lines; each **leaf** table or grid row — one with
no rows nested inside, so Hacker News's layout tables stay multi-line — is joined onto one line
capped at 240 characters. `textSource` says which path produced the text. Finished ordinary pages
sit far above the threshold (Reuters ≈95%); Gmail's two failure states sat at 4% and 2%. Two
confirming cases so far (Gmail, Google News): the threshold is a judgment with margin, the part to
watch. The same test keeps the settle loop probing while an app is still painting its shell
(Gmail's loading screen sat static at ~450 visible chars with the inbox rows hidden in the DOM);
script and style text is excluded from the readable count so Reuters' 1.2M chars of inline JSON
do not make a finished page look unpainted.

**Normalization** (`renderedText()` in `plugin-web.js`): one trimmed line per row, tab-separated
cells joined with ` · `, the separator runs that empty cells leave behind collapsed, blank lines
and consecutive repeats dropped, the usual cap and marker. `visibleText()` moved to
`plugin-web.js` and is the HTTP tier's approximation.

**Measured, 5,000-char cap:**

| Page | Article view | Text view |
|---|---|---|
| Gmail inbox | ~500 chars per message, 5–7 lines each | 142 chars per message, one line each, 2.9 s |
| Google News front | 17 lines, 3,532 of 5,016 chars spent on URLs | 208 lines, 36 headlines, no URL overhead |
| Wikipedia article | 10 paragraphs with links | 73 short lines, links lost — article view is right here |
| Reuters, Hacker News | as in v1.4.2 | read correctly; nested layout tables not flattened |
| GitHub issues, YouTube front | ~700 chars | same — these do not render in a hidden tab; no view helps |

## 🗂️ Tab Fetch — read the tab you have open

**Turn it on.** Browser Search card → **Let the assistant read my open tabs** (off by default:
tab titles and URLs are personal). Three more toggles: **Confirm before reading a tab** (on),
**Reuse my open tab when the address matches** (on), **Never open hidden tabs on sites I have
open** (off).

**How a tab is named.** `web_fetch` takes a `tab` instead of a `url`: `"active"` (the tab you are
looking at), a tab id from the new `browser_tabs` tool (title, host, URL, which is current), or a
host/title fragment. Resolution is deterministic and lives in the tool, not in the model's
judgment: **one match reads; zero or several ask.** With Chase and Bank of America both open,
"my Chase tab" reads Chase; "my bank tab" returns both and the model asks; two Chase tabs do the
same. `"active"` never resolves to the Lumispec UI itself — it asks which tab you meant.

**What a read is.** The extension runs the same page reader in your tab, in place: no navigation,
no reload, no activation, no close — your session and your scroll position are untouched, and both
views work (`text` is exact there, since a visible tab has layout). The result says
`source: "tab"`, names the tab and its last-accessed time, and the Think stream shows the listing
the model saw. A tab read never falls back to HTTP; if the tab has no readable text yet the tool
says so rather than re-fetching. The extension's own transient tabs are never listed or readable;
incognito and `chrome://` pages are excluded; a tab Chrome suspended (memory saver) is listed but
not read until you click it.

**Approval.** With **Confirm before reading a tab** on, every read goes through the same
approve/deny prompt as `run_python`, naming the tab and host. **Autorun does not bypass it** — the
risk case is a model picking a tab on its own, which is exactly when a pipeline runs unattended. A
decline reads nothing and the model is told not to retry.

**Sites you have open, on ordinary fetches.** The hidden tab remains the main path, but before
opening one the plugin now looks at your tabs on that host (only while Tab Fetch is on):

- the same address already open → your tab is read in place instead of loaded again
  (`source: "tab"`, a note says so). No prompt here: the model asked for that address by URL and a
  hidden fetch would have loaded it with the same cookies and disclosed the same content.
- the same host, another address → the hidden fetch proceeds, with your tabs on that host attached
  as `openTabs` and a hint, so the model can offer to read one instead of loading more pages on a
  site you are logged into.
- **Never open hidden tabs on sites I have open** → returns your tabs and stops; the model asks.

With the master toggle off, every hidden fetch is byte-for-byte what v1.4.2 did.

**Extension 0.7.0.** Advertises `capabilities: ['fetch', 'tabs', 'read']`; `tabs` and `read`
requests; `fetch { openTabs, reuseTabId }`. The popup gained **List my tabs** and **Read current
tab**, which show exactly what the assistant would get. The injected page functions take every
value they need as an argument and return their own errors as data, after an intermediate build
referenced an extension-scope constant from inside the page and silently turned every fetch into
an HTTP fallback.

**Validated live** with six tabs open (two GitHub, Gmail, E*TRADE, Bank of America, Chase): "my
github tab" asked between the two; "my Chase tab" and `active` (Chase focused) prompted with the
host and a decline read nothing; a GitHub tab read in place in 9 ms (4,877 chars of on-screen
text); a hidden fetch of the open `tree/dev` address was reused in 7 ms; `/pulls` on the same host
fetched hidden with both GitHub tabs as the hint; with *protect* on it stopped and named them;
tab id 999999 → "closed or not readable".

## ⚙️ Configuration

No `.env` change. Four new booleans on the Browser Search card, in `data/plugins.json` under
`browser`: `readTabs` (off), `confirmTabReads` (on), `reuseOpenTab` (on), `protectOpenSites`
(off). **Extension reload required:** `extension/manifest.json` is 0.7.0; until Chrome reloads it,
`view: "text"` is approximated from markup (the result says so) and the tab tools answer "reload
the extension".

## ✅ Validation

- `npm test`: 50/50.
- Text view, extension ≥ 0.6.5: Gmail inbox one line per message, 13 messages in the first 4,863
  characters after 1,145 characters of sidebar labels, `textSource: styleWalk`, 2 reads, 2.9 s;
  Reuters 112 lines in 2.5 s; Hacker News 95 lines in 1.8 s, rows intact; Google News, Wikipedia,
  GitHub issues and YouTube in both views for the table above.
- Tab Fetch, extension 0.7.0: the eight scenarios listed above, plus: with the old extension still
  connected the tools answered "reload" and a hidden Reuters fetch was unchanged; the Tab Fetch
  prompt lines appear only while the toggle is on.

**Known and accepted:** Gmail's sidebar labels precede the message rows because they are on
screen; the 240-char row cap stands in for a visual measurement. Pages that render nothing in a
background tab (YouTube's feed) return their shell in either view. Pagination stays
site-specific. The 10% walker threshold has two confirming cases. Tab Fetch is read-only by
design; "scroll this tab and read again" is a possible later step.
