# LLM Workbench v1.4.3

## Overview

One feature on top of v1.4.2: **`web_fetch` can now return a page as it reads on screen.** The
v1.4.2 extractor fixes made news fronts readable; the next real request — "list my top 70 Gmail
subjects" — showed the other half of the problem. Gmail loaded fine, signed in, through the
extension, and still cost 19 fetches and 16 rounds, because the article extractor keeps every
text node in the DOM and a Gmail inbox row is ~500 characters of hidden tooltips, accessibility
labels and image links around a sender and a subject the user sees as one line.

`web_fetch` takes an optional `view`: `article` (the default, unchanged) or `text`, one trimmed
line per visual row. The same request now costs about three fetches at the default cap. The
mechanism is generic — Google News reads five times denser in text view too — and nothing in it
knows a site by name. The extension changed, so **Browser Search needs one reload** on
`chrome://extensions` (the Plugins card says so until you do). No new dependencies, no `.env`
change. The README screenshot was also replaced with the full app around a news dashboard.

Seven commits on `dev` since v1.4.2 (2026-10-31), 17 files, +457 / −89.

## 👁️ `web_fetch` view: "text"

**Two views, one tool.** `view: "article"` is what every fetch did before: Readability for an
article, the headline-link list for a front page. `view: "text"` returns the page as it is laid
out on screen — hidden elements excluded, one line per visual row, table and grid cells joined
with ` · `. The tool descriptions and a routing line say when to use which: `text` for web
applications (mail, calendars, dashboards, boards) and whenever an `article` result comes back as
repeated fragments and image links; page through an application with its own date or filter URLs,
since invented pagination parameters are ignored. The result carries `view` so the Think stream
shows which ran. A parameter rather than a second tool because the model already reaches for one:
during the news run it invented `extractMode: "markdown"` on its own.

**Where the text comes from.** The extension sends `document.body.innerText` alongside the HTML.
`innerText` is computed by Chrome's layout engine, so CSS-hidden tooltips and labels are already
gone and each visual row ends in a line break — the real thing, which only a browser can produce.
The HTTP tier (Web Search & Fetch on its own, or the fallback) approximates it from the markup and
says so in `note`; it has no layout engine, so it cannot tell what a stylesheet hid.

**When Chrome has not laid the page out.** In an inactive tab Chrome skips layout for virtualized
lists, and `innerText` only returns text that has layout: Gmail's loaded inbox reported 593 chars
of `innerText` against 24K chars of readable DOM text (body minus script/style/noscript/template,
now reported as `domChars`). When `innerText` covers under 10% of the readable text, the extension
walks the DOM itself: subtrees whose computed style is `display: none` or `visibility: hidden`, or
that are `aria-hidden`, are dropped; blocks become lines; each **leaf** table or grid row — one with
no rows nested inside, so Hacker News's layout tables stay multi-line — is joined onto one line
capped at 240 characters, a row being one visual line however much text its cells hold.
`textSource` says which path produced the text and the `_tier` string mentions the walk. Finished
ordinary pages sit far above the threshold (Reuters ≈95%); Gmail's two failure states sat at 4%
and 2%. Two confirming cases so far (Gmail, Google News) — the threshold is a judgment with margin,
not a measured boundary, and is the part to watch.

**The same test drives the settle loop.** v1.4.2 made the extension read a page once its visible
text stopped growing. Gmail's loading shell sits static at ~450 visible characters for several
seconds while the inbox rows already exist in the DOM hidden, so "stopped growing" settled on the
shell. While under 10% of the readable text is on screen the page counts as still painting and the
loop keeps probing within its 6-second budget. Script and style text is excluded from the readable
count — Reuters carries ~1.2M chars of inline JSON, and counting it made a finished page look
unpainted for a few reads until that was fixed.

**Normalization** (`renderedText()` in `plugin-web.js`): rendered text becomes one trimmed line
per row, tab-separated cells joined with ` · `, the separator runs that empty cells leave behind
collapsed, blank lines and consecutive repeats dropped, the usual cap and marker applied.
`visibleText()` moved to `plugin-web.js` and is the HTTP tier's approximation.

**Measured, extension v0.6.5, 5,000-char cap:**

| Page | Article view | Text view |
|---|---|---|
| Gmail inbox | ~500 chars per message, 5–7 lines each | 142 chars per message, one line each, 2.9 s |
| Google News front | 17 lines, 3,532 of 5,016 chars spent on URLs | 208 lines, 36 headlines, no URL overhead |
| Wikipedia article | 10 paragraphs with links | 73 short lines, links lost — article view is right here |
| Reuters, Hacker News | as in v1.4.2 | read correctly; nested layout tables not flattened |
| GitHub issues, YouTube front | ~700 chars | same — these do not render in a hidden tab; no view helps |

## 🧩 Browser Search — extension v0.6.5

Besides the text channel above: the injected page functions now take every value they need as an
argument and return their own errors as data. v0.6.0 referenced an extension-scope constant from
inside the page function, which threw, and Chrome reported an undefined result; every fetch
silently fell back to HTTP as "Page script returned nothing" until the cause was found. A failure
of that class now reports itself as "page script failed: X is not defined", and a load-time scan
confirms neither injected function references module scope. Protocol fields added:
`text`, `textSource`, `domChars`.

- `npm test`: 35/35.
- Live, extension v0.6.5: Gmail inbox in text view, one line per message, 13 messages in the first
  4,863 characters after 1,145 characters of sidebar labels, `textSource: styleWalk`, 2 reads,
  2.9 s. Reuters text view 112 lines in 2.5 s, 2 reads. Hacker News 95 lines in 1.8 s, rows intact.
  Google News, Wikipedia, GitHub issues and YouTube fetched in both views for the table above.

**Known and accepted:** Gmail's sidebar labels and counts precede the message rows because they
are on screen; the snippet cell carries more text than Gmail shows, hence the 240-char row cap
rather than a visual measurement. Pages that render nothing in a background tab (YouTube's feed)
return their shell in either view. Pagination stays site-specific. The 10% walker threshold has two
confirming cases.
