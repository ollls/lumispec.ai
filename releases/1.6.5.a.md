# LLM Workbench v1.6.5.a

## Overview

Two additions after v1.6.5:

- **Print**: a Print button on every answer and under every applet, and a page that prints a
  saved markdown file.
- **Amazon Cart** *(experimental, off by default)*: the assistant searches Amazon and puts items
  into your cart in your own Chrome. It never buys.

**The Browser Search extension must be reloaded** (0.8.0 → 0.9.0) to use Amazon Cart.

Four commits on `dev` since v1.6.5 (2026-11-23), 34 files, +2,905 / −29.

## 🖨 Print

**What happened.** On 2026-11-26 a restaurant guide was followed by "please print this". The
model wrote an applet with a print button; pressing it did nothing, because applets run in a
sandboxed frame where the browser blocks printing without an error. Its fix opened a new window,
which is blocked the same way. The third turn saved a markdown file that there was no way to
print. Three turns, nothing on paper. Printing is now the page's job, not the model's.

- **Print on every answer.** Hover an answer: **Print** sits left of Troubleshoot. The answer is
  rendered again from its markdown as a black-on-white document and the print dialog opens.
  Tables get borders and repeat their header row on each page; rows, pictures and code blocks
  are not split across pages. Nothing of the chat, the tool details or the buttons is printed.
  The first heading becomes the document name, which browsers offer as the PDF file name.
- **Print under every applet**, after Full screen. It prints the applet as it looks on screen,
  with its own colours.
- **Markdown file printer.** `/print.html?file=NAME` shows a file from the project directory as
  the same document, with a Print button; add `&print=1` to open the dialog at once. The page
  also takes a file from your disk or pasted text.
- **The model knows.** A short Printing section in the system prompt tells it to point at the
  Print button instead of rebuilding the answer, and to give the printer link when it saves a
  markdown file. A printer link in the chat opens in a new tab.

**Limits.**

- Applets inside an answer are left out of the answer's printout, with a one-line note. Use the
  applet's own Print button.
- Mermaid diagrams print as their source text.
- Applets can now show `alert()` and `confirm()` dialogs: the sandbox permission that allows
  printing allows those too.

## 🛒 Amazon Cart (experimental)

A new plugin, **off by default** and marked **Experimental** in red on its card. Its on/off
state is deliberately not kept: **it is off again after every restart of the app**, and you
enable it each time you want it. Your site and pacing settings are kept. Enabling it switches
Browser Search on with it.

- **What it does.** `search` (products with price, rating, delivery and picture), `product`
  (one item with seller, features and pictures), `view` (your cart) and `add` (one item, quantity
  1–10). Everything runs in your own Chrome, signed in as you, through the Browser Search
  extension.
- **It never buys.** There is no checkout, buy or remove action. You review the cart and check
  out on Amazon yourself.
- **Every add asks first.** The approval names the title, price, seller and item number as
  Amazon shows them at that moment. Autorun does not skip it.
- **Ten results at a time.** Everything a query brought back is kept for 15 minutes, so "any
  more?" and a repeated search usually load nothing from Amazon.
- **Paced.** Amazon pages load a random 4–9 s apart by default, at most 8 in 5 minutes; three
  card fields change that. Calls the model makes in one step queue up instead of loading
  together.
- **Stops when Amazon objects.** A page saying automated access is refused starts a 30-minute
  pause during which nothing is loaded and the card turns amber.
- **`web_fetch` is turned away from Amazon pages** while the plugin is on, so they are loaded
  only by the paced tool.

**Why experimental.**

- **Amazon refused automated access three times on 2026-11-25** while this was being built,
  once after 19 paced loads over 40 minutes. Pacing lowers the odds; it does not prevent the
  notice.
- **Adding to the cart has not been run against the live site end to end.** The selectors were
  read from live pages, but the click itself and the layout of an active cart row are
  unverified.
- The plugin asks the model not to request Amazon from `run_python`; nothing enforces that.

Full guide: [`docs/AMAZON_CART.md`](../docs/AMAZON_CART.md).

**For developers.** Two generic plugin flags: `experimental: true` (the red label) and
`sessionOnly: true` (saved `enabled` is turned off at startup, other settings kept). The
extension's `fetch` takes `actions: [{ require } | { select, value } | { click }]`, advertised
as the `act` capability: at most six steps, run in a hidden tab the extension opened, never in a
tab of yours.

## ✅ Validation

`npm test`: 253/253, 61 more than v1.6.5 with the engine fixtures added since: 27 for Amazon
Cart, 5 for the printer, the rest for the search-engine fixtures and the extension bridge.

`npm run check:engines` on 2026-11-26: DuckDuckGo, Brave, Bing and Google all read correctly.

Print, in headless Chrome on 2026-11-26: the saved guide came out of `/print.html` as a
two-page PDF with its table intact, and the answer path built its document with the table on a
white page. **Not tested:** the print dialog in a visible browser, and Firefox.

Amazon Cart, live on 2026-11-26: eight searches in one turn returned 72 products, each with
item number, price and picture, and no refusal. That session is also where the queueing fault
was found (seven page loads where four were needed) and fixed; the fix is covered by tests, not
by a second live run.

The system prompt gains the Printing section, so the first turn after the upgrade re-reads it.
No `.env` change.
**Upgrade:** `git pull` → restart → **reload the extension** at `chrome://extensions` (the
Browser Search card shows a button for it) → hard-reload the page.
