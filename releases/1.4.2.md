# LLM Workbench v1.4.2

## Overview

A fix release on top of v1.4.1 about one thing: **what `web_fetch` hands the model**. Two days of
news-digest runs through Browser Search exposed a chain of defects, each of which made a page that
Chrome had rendered perfectly well arrive at the model as something else — nothing, a login screen,
summaries with every headline missing, or a list cut in the middle of a headline. Each was
diagnosed on a saved copy of the real page, fixed generically, and measured on nine other sites
before shipping. Nothing in the chat UI, the pipeline, the finance tools or the Obsidian exporter
changed behaviour; the v1.4.1 and v1.4.0 notes still describe everything else.

The extension changed, so **Browser Search needs one reload** on `chrome://extensions` after
pulling (the Plugins card says so until you do). No new dependencies, no `.env` change.

Seven commits on `dev` since v1.4.1 (2026-10-29 → 2026-10-31), 24 files, +873 / −87.

## 🌐 Web fetch — pages the extractor used to lose

**`<template>` blocks.** The NYT homepage embeds a 100K-char interactive inside `<template>`.
linkedom reports template contents as text, so Readability scored that one block as the whole
article and Turndown then rendered it as nothing: a page with 130K chars of visible text came out
as 0 chars, the plugin called it thin, and fell back to HTTP — which got a 403 "enable JS" shell
that the model reported as "the homepage blocks non-JS access". `htmlToMarkdown()` now removes
`<template>` elements before anything scores the page, and falls back to the whole body whenever
Readability's pick renders as empty, not only when it returns null.

**Index pages.** Homepages, section fronts and date archives defeat Readability by design: every
headline is a paragraph wrapped in a link, and Readability prunes link-dense blocks as "related
links", so it returned the story summaries with every headline missing — NYT homepage 0 of 91
headlines kept, Guardian `/world/<date>` 0 of 30, Reuters 0 of 90. The detector measures that loss
directly: a page counts as an index when headline-length link text (≥25 chars) is at least 20% of
its text, under 30% of those links survive in Readability's output, and Readability kept under 70%
of the page text. Such pages render as `- [headline](absolute url) — summary` lines under an
`Index page: N linked stories.` header. Measured on the sample set, article pages (BBC, Wikipedia,
Python docs: 2–6% link text, 76–94% kept) and homepages Readability already reads well (BBC front,
Guardian front, Hacker News: 51–96% of links kept) are untouched. The share bound started at 30%;
Reuters straddled it across renders of the same page (0.31 light, 0.24 with more summaries loaded)
and flipped run to run, hence 20% plus the text-kept guard.

**The per-fetch cap is a setting.** The 4,000-char cap on fetch markdown was a literal since the
March refactor, and a digest pipeline lost one headline per source to its mid-line cut. It is now
**Max chars per fetched page** on the Web Search & Fetch card and, editing the same stored entry,
on the Browser Search card (the one in use while the extension supersedes the web group). Default
4,000 as before, range 1,000–50,000, applied by both fetch paths. The card says why the default is
modest: ≈1 token per 4 chars, kept in context for the rest of a chat; pipeline steps are isolated
and can afford more.

## 🧩 Browser Search — extension v0.5.0

Gmail, signed in, was reported as "the browser session isn't signed in". The saved page proves
otherwise — its title was `Inbox (4,764) - … - Gmail` — and the sequence that turned it into a login
screen had four links. All four are fixed.

- **Strip dead markup before the size cap.** Gmail ships ~1.9M chars of inline CSS in the document
  head; the extension's 2M-char cap fell inside that stylesheet and the `<body>` never left Chrome.
  The extension now serializes a copy of the DOM minus `script`, `style`, `noscript`, `template`
  and `svg` — the server deletes those before reading anyway, and on the sample sites they were
  43–100% of the bytes (Gmail 100%, NYT 75%, Guardian section 75%, BBC article 70%; Wikipedia 8%,
  Hacker News 0%). The cap is 4M on what remains, so only content can hit it, and `htmlChars`
  reports the raw size alongside.
- **Read pages after they settle, not at 200 characters.** The old loop stopped at the first read
  with 200+ chars of visible text — a proxy for "something rendered" that holds for server-rendered
  pages and fails for apps that paint progressively: Gmail's header crossed the line seconds before
  the message list existed (444 chars accepted as final). A page with real text is now probed every
  0.6 s until its visible text stops growing, bounded at 6 s; thin or walled pages keep the old
  retry schedule. Server-rendered pages settle on the first probe (Reuters: 2 reads, ~2 s). The
  result carries `reads`.
- **A rendered page never falls back to HTTP.** The thin-page fallback decided on the *extractor's*
  output, which cannot tell "the browser got nothing" from "the browser got everything and we lost
  it" — and the HTTP tier has no browser cookies, so re-fetching a signed-in page hands the model a
  login screen that looks like a real answer. If Chrome reported ≥500 chars of visible text, the
  call now returns that visible text (one line per block, same cap) with a note, and never falls
  back. When the fallback does run and its result reads like a sign-in page, it carries
  `loginWall: true` and a note that this is not evidence the user is logged out, naming the page
  Chrome actually reached.
- **CAPTCHAs inside an iframe.** Reuters answered the hidden tab with a DataDome challenge that
  lives entirely in a cross-origin iframe: zero visible text, no wall phrase to match, reported as
  "browser returned 11 chars". `detectWall()` now checks iframe `src` / `title` on thin pages
  (DataDome, Cloudflare, hCaptcha, reCAPTCHA, PerimeterX, Arkose) and names the vendor with the
  one-time fix: open the site in a normal tab, pass the check, retry. A real page with an embedded
  reCAPTCHA widget in a form is left alone.
- **Evidence survives.** A rendered page the extractor cannot read is saved to
  `logs/browser-debug/fetch-thin-*.html`, and the reason names the file, the visible text count and
  whether the cap truncated the page — the reason alone could not be debugged after the fact. For
  pages the extractor reads *badly* rather than not at all, the card has a **Save every fetched
  page** toggle that dumps each extension fetch to `logs/browser-debug/fetch-<host>-*.html`. Off by
  default; every parser change in this release was made against such a dump.

## 🎨 Applets — a dropped last token

A 19K-char HTML dashboard rendered as plain tables with no styling and no ticker script. The stored
answer ended in `</applet` — the model sampled end-of-sequence instead of the final `>` (finish
reason `stop`, no length cut, every stream delta delivered; asked directly, llama-server returns
the tag intact). The strict regex matched nothing, so the HTML went through the markdown path and
DOMPurify stripped its styles and scripts, and the raw 19K went back into the model's context on
every later turn instead of the one-line placeholder. A closing tag that is the last token of an
answer is the normal shape for "render this as a dashboard", so one dropped token must not cost
the block: `src/services/applets.js` is now the one definition, accepting `</applet>` or end of
text as the terminator and stripping a cut-short closer. The history filter and the Obsidian
exporter use it; `app.js` carries a copy. The final render is tolerant; streaming renders keep the
strict form so a half-streamed block stays text until the final event.

## 🛠️ Tool-call parser — two Qwen3.8 shapes

On 2026-10-29 one conversation spent 17 rounds re-prompting the model for a tool call it never
managed to parse. Two mechanical defects: the opening quote of a key dropped after a comma and
newline (`"name": "x",\narguments": {…}`), and the tool named under `"function"` instead of
`"name"`. `normalizeToolCallKeys()` repairs both before the retry prompt is considered. And the
retry itself is now bounded: after `MAX_REPAIR_ROUNDS` (3) consecutive unparseable tool calls, both
loops break to the forced answer with a "your last N tool calls were never executed" instruction
instead of burning the remaining rounds (route log `end` / `repair-limit`).

## 🧩 Plugin system

- Generic card fields gain `type: 'number'` (`min` / `max` / `step`), and a field may target
  another group's stored entry (`group`) and carry its own current value (`value`). The fetch cap
  is the consumer: one value on `web`, shown on two cards. Config-only updates to a superseded
  group were already allowed.
- `beforeCard()` is used by the web and browser plugins to refresh that value for their
  synchronous card descriptors.

## ⚙️ Configuration

No `.env` change. Two new card settings, both in `data/plugins.json`:

- **Web Search & Fetch / Browser Search → Max chars per fetched page** (`web.fetchMaxChars`,
  default 4000, 1000–50000).
- **Browser Search → Save every fetched page to logs/browser-debug/** (`browser.dumpPages`,
  default off).

**Extension reload required:** `extension/manifest.json` is 0.5.0. Until Chrome reloads it the
Plugins card reads "outdated, this checkout ships v0.5.0" and the old read loop and 2M cap apply.

## ✅ Validation

- `npm test`: 34/34.
- Live, extension v0.5.0: NYT homepage through the extension tier in ~3.3 s as a 34-story index
  list with URLs and summaries (was 0 chars → HTTP 403 shell); Reuters five consecutive fetches, all
  the 58-story index in 2.0–2.7 s with 2 reads (was summaries with no headlines, flipping run to
  run); Gmail inbox loads signed in and no longer becomes a login screen.
- A news-digest pipeline over ten sources, every fetch through the extension in 2–6 s: BBC,
  Guardian and CNN produce the same shape as before this release; Fox, NPR and Reuters went from
  0–2 headline lines to 16–24 under the same cap.
- Offline, against saved pages: the index detector on 13 copies (4 Reuters renders, NYT, Guardian
  date page, The Verge, BBC front, Guardian front, Hacker News, BBC article, Wikipedia, Python
  docs) flips exactly the pages whose headlines Readability drops.

**Known and accepted:** index lists can open with one or two promo-bar links before the first
headline (Reuters: two of sixteen); filtering them generically would mean guessing at URL depth.
The cap still cuts mid-line, so a list longer than the cap ends in a partial headline; URLs with
tracking parameters and ad-rail links spend cap space they do not earn. All three are candidates
for a later release.
